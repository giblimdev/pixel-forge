Version : 3.0 — Réalité du projet livré
Plateforme : Vercel (serverless)
Moteur : Sharp 0.35.5 côté serveur

1. Présentation des outils PixelForge
PixelForge regroupe 12 outils répartis en 5 familles plus 1 outil transversal d'analyse. Chaque outil est autonome et partage les briques communes (import, file d'attente, comparaison avant/après, export).

Famille 01 — CONVERTIR (1 outil)
Outil 01 — Convertisseur universel
Changer le format d'une image. Entrées : JPEG, PNG, GIF, AVIF, TIFF, WebP, SVG (rasterisé). Sorties selon capacités Sharp réelles : JPEG, PNG, WebP, AVIF, TIFF. Contrôle qualité 1-100, modes lossy/lossless/near-lossless uniquement si le format les supporte. Gestion EXIF/ICC. Redimensionnement facultatif (cover/contain/inside). Traitement par lot, aperçu avant/après, export ZIP.
Intérêt : WebP réduit de 25-35 % à qualité visuelle égale — premier besoin des développeurs web.

Famille 02 — OPTIMISER (4 outils)
Outil 02 — Optimiseur intelligent
Compression et qualité adaptatives, quantification, strip des métadonnées inutiles, redimensionnement proportionnel ou libre, recadrage intelligent selon un ratio. Poids cible configurable (ex. 200 Ko) — c'est une cible, pas une garantie absolue. Résultats : poids initial/final, dimensions initiales/finales, économie en Ko et %. Comparaison visuelle avant/après. SSIM retiré (non natif dans Sharp) — remplacé par entropie + écart-type.

Outil 03 — Compresseur JPEG/PNG
Réduire le poids sans changer de format. Réglage qualité JPEG, palette/quantification PNG, préservation transparence PNG. Affichage résultats et différences de poids.

Outil 04 — Redimensionnement par lot
Traiter N images : largeur/hauteur cibles, largeur ou hauteur maximale, respect du ratio ou dimensions libres, modes cover/contain/inside, génération de plusieurs variantes (320/640/1280).

Outil 05 — Recadrage intelligent (smart crop)
Recadrage automatique selon un ratio (16:9, 1:1, 4:3, personnalisé) via stratégie Sharp attention ou entropy (heuristique d'entropie, PAS de reconnaissance sémantique). Aperçu avant traitement, ratio modifiable.

Famille 03 — ÉDITER (3 outils)
Outil 06 — Éditeur de recadrage manuel
Recadrage libre et ratios prédéfinis, rotation 90/180/270, retournement H/V, saisie numérique des dimensions/coordonnées, aperçu. Basé sur react-easy-crop (~30 Ko, choisi à la place de Konva ~180 Ko). Pas de système de calques (hors périmètre).

Outil 07 — Suppression d'arrière-plan (détourage)
Périmètre restreint : fonds unis. Pipette couleur, tolérance réglable (distance RGB euclidienne normalisée), détection/remplacement par transparence, antialiasing/lissage des contours. Export PNG alpha. Pas d'IA sémantique — détourage sur fond uni uniquement.

Outil 08 — Retouche rapide + filigrane
Réglages globaux uniquement : luminosité, contraste, saturation, teinte, flou, netteté, niveaux de gris. Pas d'édition au pixel. Filigrane texte (position 9 ancrages, opacité, taille relative). Traitement par lot, aperçu avant export.

Famille 04 — GÉNÉRER (3 outils)
Outil 09 — Générateur de favicons
Source PNG/JPEG/SVG. Tailles ICO : 16/24/32/48/64/128/256 px. Sorties : favicon.ico (multi-résolutions), apple-touch-icon.png, android-chrome-192x192.png, android-chrome-512x512.png, manifest.webmanifest. Assemblage ICO fait par lib/favicon/ico-builder.ts (implémentation custom, 0 dépendance npm) — pas de png-to-ico. Le manifeste est généré depuis options validées. Export ZIP via @vercel/blob.

Outil 10 — Générateur de placeholders
LQIP en Base64, BlurHash, SVG flouté, Base64. Aperçu et copie/export du code. Chaque type expose clairement son format de sortie et son intégration (background-image CSS, attribut blurhash, SVG inline). Package blurhash installé.

Outil 11 — Extracteur de palettes
Extraction des N couleurs dominantes (1-10) via sharp.stats() + clustering par bucketing RGB 32×32×32. Présentation HEX/RGB/ratio. Export CSS variables, Tailwind config, JSON.

Famille 05 — ANALYSER (1 outil transversal)
Outil 12 — Analyse & métadonnées
Lecture dimensions, format, poids, résolution, transparence, espace colorimétrique. Lecture EXIF structurée : appareil (make/model), date, orientation, logiciel, GPS. Consultation profils ICC. Suppression des métadonnées (vie privée) avec choix explicite. Endpoint POST unique avec ?action=analyze|strip.

Fonctionnalités transversales (obligatoires, non dupliquées)
Image Queue : drag & drop multi (HTML5 natif), Ctrl+V, miniatures, validation MIME/extension/taille (25 Mo), statuts (pending/running/success/partial/error), suppression individuelle/globale.

Image Comparison : slider avant/après, poids/dimensions initiaux/finaux, économie Ko et %, damier transparence.

Export Manager : téléchargement individuel, ZIP groupé, conservation des noms, suffixes explicites, gestion collisions, organisation par format/résolution.

History (localStorage) : historique des traitements, branchement sur /pixel/dashboard, 50 entrées max, 0 donnée serveur.

2. Règles d'architecture (non négociables)
Sharp exclusivement côté serveur. Aucun composant client n'importe sharp.

Les composants client appellent les routes HTTP /api/images/*.

Les formats proposés dans l'UI proviennent du registre des capacités du moteur (FORMAT_CAPABILITIES).

Validation répétée côté serveur — la validation navigateur est UX, jamais protection.

Types TypeScript = contrats ; schémas Zod = validation runtime.

La file d'attente ne traite pas d'images — elle gère uniquement l'état.

Les URL temporaires (URL.createObjectURL) sont libérées lors de la suppression/démontage.

Fichiers d'origine jamais écrasés. Chaque résultat est un nouvel artefact avec suffixe (-webp, -compressed, -640w, -clean).

Les traitements retournent des erreurs structurées : { code, message, details? }.

Les limites sont centralisées dans lib/validators/image-limits.ts.

Runtime Node.js implicite : export const runtime = "nodejs" est interdit avec cacheComponents activé (Next.js 16). Sharp fonctionne car Node.js est le runtime par défaut.

export const maxDuration = 60 sur chaque route API.

Limites fonctionnelles explicites (à NE PAS promettre)
Retouche = ajustements globaux, pas de peinture pixel.

Détourage = fonds unis uniquement, pas d'IA sémantique.

Smart crop = heuristique entropy/attention, pas de détection d'objets.

ICO = assemblage par lib/favicon/ico-builder.ts (custom, 0 dépendance).

SSIM retiré — non natif dans Sharp. Métriques affichées : poids, dimensions, entropie, écart-type.

GIF animé = première frame par défaut.

SVG = entrée rasterisée uniquement ; sanitizer obligatoire.

Poids cible = cible, pas garantie ; nombre d'itérations borné.

🎨 Partie II — Améliorations UI/UX des outils
Voici une analyse des améliorations UI/UX recommandées pour chacun des 12 outils et les composants transversaux. Ces points sont optionnels mais amélioreraient significativement l'expérience utilisateur.

A. Améliorations transversales (12 outils)
A.1 — Feedback de progression granulaire
Problème actuel : pendant submit(), la barre est indéterminée (value={null}) — l'utilisateur ne sait pas où en est le lot.

Amélioration : exposer une progression réelle par fichier.

tsx
// Dans chaque hook, remplacer setStatus("running") par :
setStatus(item.source.id, "running");
setProgress(item.source.id, 0);

// Puis, à chaque fichier traité :
setProgress(item.source.id, (index + 1) / targets.length * 100);
Bénéfice : pour un lot de 20 fichiers, l'utilisateur voit 5/20, 10/20, etc.

A.2 — Raccourcis clavier par outil
Problème actuel : l'utilisateur doit cliquer sur chaque bouton.

Amélioration : ajouter des raccourcis globaux via useEffect :

Touche	Action	Contexte
Ctrl+Enter	Lancer le traitement	Toutes les pages outil
Ctrl+Shift+C	Vider la file	Toutes les pages outil
Esc	Fermer les résultats	Toutes les pages outil
← / →	Naviguer entre les résultats	Pages avec résultats
tsx
useEffect(() => {
  function handleKeyDown(e: KeyboardEvent) {
    if ((e.ctrlKey || e.metaKey) && e.key === "Enter") {
      e.preventDefault();
      if (pendingCount > 0 && !running) void submit();
    }
    if ((e.ctrlKey || e.metaKey) && e.shiftKey && e.key === "C") {
      e.preventDefault();
      clear();
    }
  }
  window.addEventListener("keydown", handleKeyDown);
  return () => window.removeEventListener("keydown", handleKeyDown);
}, [pendingCount, running, submit, clear]);
A.3 — Confirmation avant traitement massif
Problème actuel : cliquer sur "Convertir" avec 20 fichiers lancés traite tout sans confirmation.

Amélioration : window.confirm si pendingCount > 10.

function handleSubmit() {
  if (pendingCount > 10) {
    const confirmed = window.confirm(

Problème actuel : les résultats sont affichés dans l'ordre d'arrivée, pas de tri.

Amélioration : ajouter un tri par nom, poids, date.

A.8 — Indicateur de poids avant/après en temps réel
Problème actuel : ComparisonStats affiche l'économie uniquement après traitement.

Amélioration : afficher une estimation avant traitement (basée sur le format cible).

tsx
// Avant submit :
const estimate = useMemo(() => {
  if (pendingCount === 0) return null;
  const totalBytes = items
    .filter((i) => i.status === "pending")
    .reduce((sum, i) => sum + i.source.sizeBytes, 0);
  const factor = options.format === "webp" ? 0.7 : options.format === "avif" ? 0.5 : 0.9;
  return Math.round(totalBytes * factor);
}, [items, options.format, pendingCount]);

{estimate !== null && (
  <p className="text-xs text-[var(--pf-muted)]">
    Estimation : ~{formatSize(estimate)} après conversion.
  </p>
)}
