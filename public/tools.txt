tool 1 — Conversion de format universelle
Description : 
Convertir entre tous les formats supportés par sharp : JPEG ↔ PNG ↔ WebP ↔ AVIF ↔ TIFF ↔ GIF
Conversion d'images JPEG, PNG, GIF, AVIF, TIFF en WebP avec contrôle de la qualité (1-100), et svg
du mode (lossy / lossless / near-lossless), des métadonnées (EXIF, ICC) et du redimensionnement (fit cover / contain / inside). Traitement par lot avec files d'attente, aperçu avant/après et téléchargement ZIP.
Intérêt : WebP réduit le poids de 25 à 35 % à qualité visuelle égale par rapport au JPEG. C'est le premier besoin des développeurs web.

tool 2 — Optimisation du poids et de la taille
Description : Réduction du poids par compression intelligente 
(qualité adaptative, quantization, strip des métadonnées inutiles), redimensionnement proportionnel ou libre, 
et recadrage intelligent (smart crop basé sur l'entropie). Comparaison avant/après (poids, dimensions, qualité SSIM). 
Seuils cibles configurables (ex. « ne pas dépasser 200 Ko »).
Intérêt : Chaque kilo-octet économisé améliore le SEO, le temps de chargement et l'expérience mobile.

tool 3 — Génération de favicons complets (ICO + PNG + manifest)
Description : Création de fichiers .ico à partir d'une image source (PNG, JPEG, SVG) avec sélection des tailles (16, 24, 32, 48, 64, 128, 256) dans un seul fichier ICO. Détection automatique des tailles recommandées pour Windows / navigateurs. Aperçu de chaque résolution et validation de la transparence.
À partir d'une image source, générer tous les favicons nécessaires : favicon.ico, apple-touch-icon.png, android-chrome-192x192.png, android-chrome-512x512.png, manifest.webmanifest. ZIP téléchargeable.
Intérêt : Les favicons et icônes d'application sont fastidieux à produire. Un générateur multi-résolutions fiable évite les allers-retours avec des outils en ligne qui ajoutent des filigranes.

tool 4 — PNG transparents et détourage
Description : Suppression d'un fond uni (couleur choisie par pipette) avec tolérance réglable, remplacement par transparence, lissage des contours (anti-aliasing) et édition manuelle au pinceau gomme. Détection automatique des arrière-plans unis (blanc, noir, vert). Export PNG avec alpha.

Intérêt : Les PNG transparents sont partout : logos, mockups, illustrations. Le détourage manuel est chronophage ; un détourage automatique sur fond uni couvre la majorité des cas.

tool 5 — Compression PNG / JPEG (sans changer de format)
Description : Réduire le poids d'un PNG ou JPEG en gardant le même format. Utile pour les assets qui doivent rester en PNG (transparence) ou JPEG (compatibilité).

tool 6 — Redimensionnement par lot
Description : Redimensionner N images vers des dimensions cibles (largeur max, hauteur max, fit cover/contain/inside). Génération de plusieurs tailles (ex. 320/640/1280 pour le responsive).

tool 7 — Recadrage intelligent (smart crop)
Description : Recadrer automatiquement une image vers un ratio (16:9, 1:1, 4:3) en gardant le sujet au centre. Basé sur sharp.strategy.attention (détection d'entropie).

tool 8 — Extraction / suppression de métadonnées EXIF
Description : Voir les EXIF (GPS, appareil, date) d'une image et les supprimer (vie privée). sharp.withMetadata() / sharp.strip().

tool 9 — Génération de placeholder LQIP / blurhash
Description : À partir d'une image, générer un placeholder ultra-léger (LQIP base64, blurhash, ou SVG flouté) à intégrer dans une page avant le chargement complet.

tool 10 — Watermark / filigrane
Description : Ajouter un logo ou un texte sur N images (position, opacité, taille). Traitement par lot, aperçu.

tool 11 —  Éditeur de couleur / palette à partir d'image
Description : Extraire les 5 couleurs dominantes d'une image (via sharp.stats() + clustering) et générer une palette exportable (CSS variables, Tailwind, JSON).

tool 12 —  Retouche rapide (faisable avec sharp)
Ajustements globaux sur l'image : luminosité, contraste, saturation, teinte, flou, netteté, niveaux de gris. Traitement par lot, pas d'édition au pixel. C'est exactement les 3 outils que je te proposais dans le message précédent (Teinte, Flou, Luminosité).

tool 13  —  Transform recadrage manuel d'image

UX — Dépôt multi-fichiers par glisser-déposer
Description : Zone de dépôt pour plusieurs images avec gestion onDrop, onDragOver, onPaste (Ctrl+V). Validation côté client (extension + taille ≤ 25 Mo + type MIME image/*). Ajout à une file d'attente avec miniature, poids et format détecté. File vidable en un clic.

Intérêt : L'UX de dépôt est la première impression de l'utilisateur. Un drag & drop fluide avec feedback immédiat évite l'abandon.

UX — Comparaison avant / après avec slider
Description : Slider horizontal qui superpose l'image originale et l'image traitée, avec affichage en temps réel du poids de chaque version et du taux d'économie. Indicateur SSIM (via sharp.stats()) pour quantifier la similarité visuelle. Fond damier pour les PNG transparents.

Intérêt : La validation visuelle avant téléchargement est essentielle pour les designers et créateurs. C'est la garantie que la compression n'a pas dégradé l'image.



01 — CONVERTIR

1 outil

Changer le format des images.

01. Convertisseur universel

JPEG, PNG, WebP, AVIF, TIFF, GIF et SVG en entrée selon les capacités du moteur. Conversion vers les formats de sortie pris en charge.


02 — OPTIMISER

4 outils

Réduire le poids et adapter les dimensions.

02. Optimiseur intelligent

Optimisation automatique selon un poids cible, une qualité souhaitée ou un niveau de compression.

03. Compresseur JPEG / PNG

Compression sans changement de format, avec contrôle de qualité et de palette PNG.

04. Redimensionnement par lot

Dimensions fixes, largeur maximale, hauteur maximale, proportions et génération de plusieurs variantes.

05. Recadrage intelligent

Recadrage automatique selon un ratio avec détection du sujet et positionnement pertinent.


03 — ÉDITER

3 outils

Modifier l'apparence et la composition.

06. Éditeur de recadrage

Recadrage manuel, rotation, retournement, ratios prédéfinis et cadrage libre.

07. Suppression d'arrière-plan

Détourage sur fond uni, pipette, tolérance, lissage des contours et gomme manuelle.

08. Retouche et filigrane

Réglages colorimétriques, luminosité, contraste, saturation, teinte, netteté, flou, niveaux de gris et ajout de watermark.


04 — GÉNÉRER

3 outils

Créer des ressources graphiques et techniques.

09. Générateur de favicons

ICO multi-résolutions, PNG, Apple Touch Icon, Android Chrome et manifest.

10. Générateur de placeholders

LQIP, BlurHash, SVG flouté et Base64 pour les applications web.

11. Extracteur de palettes

Extraction des couleurs dominantes et export CSS, Tailwind et JSON.


05 — ANALYSER


Comprendre les propriétés et les informations d'une image.

Analyse des images et métadonnées

Dimensions, format, poids, résolution, transparence, EXIF, GPS, appareil, date, profils ICC et suppression des métadonnées.




2. Les fonctionnalités transversales
Certaines fonctions ne doivent surtout pas être développées comme des outils indépendants. Elles doivent être disponibles dans plusieurs modules.

A. Gestionnaire de fichiers et file d'attente


Image Queue

Le point d'entrée commun de PixelForge.
- Glisser-déposer multiple.
- Coller depuis le presse-papiers (Ctrl + V).
- Miniatures et informations des fichiers.
- Validation MIME, extension et taille (25 Mo).
- Suppression individuelle ou globale.
- Statut : en attente, en cours, terminé, erreur.


B. Comparateur avant / après

Image Comparison

Un composant réutilisable dans le convertisseur, l'optimiseur et l'éditeur.
- Slider de comparaison.
- Affichage côte à côte.
- Poids initial et final.
- Dimensions initiales et finales.
- Économie en Ko et en pourcentage.
- Fond damier pour la transparence.


C. Exportation et téléchargement

Export Manager
- Téléchargement individuel.
- Téléchargement groupé ZIP.
- Conservation des noms de fichiers.
- Gestion des noms et suffixes.
- Organisation des fichiers par format ou résolution.

PixelForge — Roadmap de développement complète et consolidée
Version : 2.0 (fusion des deux documents précédents)
Périmètre : application Next.js de conversion, optimisation, édition, génération et analyse d'images.
Moteur principal : Sharp côté serveur.
Principe directeur : Une interface par outil, des composants transversaux partagés, une validation centralisée et un moteur d'image unique côté serveur.

1. Présentation des outils PixelForge
PixelForge regroupe 11 outils répartis en 5 familles, plus 1 outil transversal d'analyse. Chaque outil est autonome mais partage les briques communes (import, file, comparaison, export).

Famille 01 — CONVERTIR (1 outil)
Outil 01 — Convertisseur universel
Changer le format d'une image. Entrées : JPEG, PNG, GIF, AVIF, TIFF, WebP, SVG (rasterisé). 
Sorties selon capacités Sharp réelles : JPEG, PNG, WebP, AVIF, TIFF. 
Contrôle qualité 1-100, modes lossy/lossless/near-lossless uniquement si le format les supporte. 
Gestion EXIF/ICC. Redimensionnement facultatif (cover/contain/inside). Traitement par lot, aperçu avant/après, export ZIP.
Intérêt : WebP réduit de 25-35 % à qualité visuelle égale — premier besoin des développeurs web.

Famille 02 — OPTIMISER (4 outils)
Outil 02 — Optimiseur intelligent
Compression et qualité adaptatives, quantification, strip des métadonnées inutiles, 
redimensionnement proportionnel ou libre, recadrage intelligent selon un ratio. 
Poids cible configurable (ex. 200 Ko) — c'est une cible, pas une garantie absolue. 
Résultats : poids initial/final, dimensions initiales/finales, économie en Ko et %. 
Comparaison visuelle avant/après. SSIM uniquement si une méthode fiable est intégrée et testée.
npm install ssim.js 

Outil 03 — Compresseur JPEG/PNG
Réduire le poids sans changer de format. Réglage qualité JPEG, palette/quantification PNG, préservation transparence PNG. Affichage résultats et différences de poids.

Outil 04 — Redimensionnement par lot
Traiter N images : largeur/hauteur cibles, largeur ou hauteur maximale, respect du ratio ou dimensions libres, modes cover/contain/inside, génération de plusieurs variantes (320/640/1280).

Outil 05 — Recadrage intelligent (smart crop)
Recadrage automatique selon un ratio (16:9, 1:1, 4:3, personnalisé) 
via stratégie Sharp attention ou entropy (heuristique d'entropie, PAS de reconnaissance sémantique). 
Aperçu avant traitement, ratio modifiable.

Famille 03 — ÉDITER (3 outils)
Outil 06 — Éditeur de recadrage manuel
Recadrage libre et ratios prédéfinis, rotation 90/180/270, retournement H/V, saisie numérique des dimensions/coordonnées, 
aperçu, historique local (cadrage uniquement, pas un système de calques).

Outil 07 — Suppression d'arrière-plan (détourage)
Périmètre restreint : fonds unis. Pipette couleur, tolérance réglable, détection/remplacement par transparence, 
antialiasing/lissage des contours, gomme manuelle pour corriger les résidus. Export PNG alpha. Ne PAS promettre un détourage IA de sujets complexes.

Outil 08 — Retouche rapide + filigrane
Réglages globaux uniquement : luminosité, contraste, saturation, teinte, flou, netteté, niveaux de gris. Pas d'édition au pixel. Filigrane texte ou logo (position 9 ancrages, opacité, taille relative). Traitement par lot, aperçu avant export.

Famille 04 — GÉNÉRER (3 outils)
Outil 09 — Générateur de favicons
Source PNG/JPEG/SVG. Tailles ICO : 16/24/32/48/64/128/256 px. Sorties : favicon.ico (multi-résolutions), apple-touch-icon.png, android-chrome-192x192.png, android-chrome-512x512.png, manifest.webmanifest. Sharp prépare les PNG de chaque taille ; un encodeur ICO complémentaire (png-to-ico) assemble le conteneur. Aperçu multi-résolutions, contrôle transparence, export ZIP. Le manifeste est généré depuis options validées (pas de JSON arbitraire).

Outil 10 — Générateur de placeholders
LQIP en Base64, BlurHash, SVG flouté. Aperçu et copie/export du code. Chaque type expose clairement son format de sortie et son intégration (background-image CSS, attribut blurhash, SVG inline).

Outil 11 — Extracteur de palettes
Extraction des 5 couleurs dominantes via sharp.stats() + clustering. Présentation HEX/RGB/ratio. Export CSS variables, Tailwind, JSON.

Famille 05 — ANALYSER (1 outil transversal)
Outil 12 — Analyse & métadonnées
Lecture dimensions, format, poids, résolution, transparence, espace colorimétrique. Lecture EXIF : GPS, appareil, date. Consultation profils ICC. Suppression des métadonnées (vie privée) avec choix explicite conservation/suppression lors des conversions.

Fonctionnalités transversales (obligatoires, non dupliquées)
Image Queue : drag & drop multi, Ctrl+V, miniatures, validation MIME/extension/taille (25 Mo), statuts (pending/running/done/error), suppression individuelle/globale.

Image Comparison : slider avant/après, poids/dimensions initiaux/finaux, économie Ko et %, damier transparence.

Export Manager : téléchargement individuel, ZIP groupé, conservation des noms, suffixes explicites, gestion collisions, organisation par format/résolution.

2. Règles d'architecture (non négociables)
Sharp exclusivement côté serveur. Aucun composant client n'importe sharp, directement ou indirectement.

Les composants client appellent les routes HTTP (/api/images/*) ou une couche applicative client clairement définie.

Les formats proposés dans l'UI proviennent du registre des capacités du moteur. Ne pas afficher une conversion que le moteur ne sait pas produire.

Validation répétée côté serveur. La validation navigateur est UX, jamais protection.

Types TypeScript = contrats ; schémas Zod = validation runtime. Ne pas confondre.

La file d'attente ne traite pas d'images — elle gère uniquement l'état.

Les URL temporaires (URL.createObjectURL) sont libérées lors de la suppression/démontage.

Les fichiers d'origine ne sont jamais écrasés. Chaque résultat est un nouvel artefact avec suffixe (-webp, -compressed, -640w, etc.).

Les traitements retournent des erreurs structurées (code stable, message utilisateur, détails techniques non sensibles).

Les limites (25 Mo, dimensions max, nombre de pixels, nombre de fichiers/batch) sont centralisées dans lib/validators/image-limits.ts.

Routes API en runtime = "nodejs" (Sharp ne fonctionne pas sur Edge).

export const maxDuration = 60 sur chaque page/route outil (Vercel timeout défaut à 10s).

Limites fonctionnelles explicites (à NE PAS promettre)
Retouche = ajustements globaux, pas de peinture pixel.

Détourage = fonds unis uniquement, pas d'IA sémantique.

Smart crop = heuristique entropy/attention, pas de détection d'objets.

ICO = assemblage par encodeur complémentaire (png-to-ico), Sharp seul ne suffit pas.

SSIM ≠ natif sharp.stats() — afficher uniquement si implémenté et testé, sinon retirer la métrique.

GIF animé = première frame par défaut ; si non préservé, l'indiquer explicitement.

SVG = entrée rasterisée uniquement ; sanitizer obligatoire (svg-sanitizer.ts).

Poids cible = cible, pas garantie ; nombre d'itérations borné.

10. Stratégie de tests
Tests ajoutés au fur et à mesure, jamais reportés à la fin.

10.1 Validateurs
Fichier conforme / vide.

Extension incohérente avec contenu.

MIME falsifié.

Fichier > 25 Mo.

Image aux dimensions/pixels excessifs.

Image corrompue.

SVG contenant éléments dangereux.

10.2 Moteur
Conversion JPEG, PNG, WebP.

Préservation transparence.

Resize cover/contain/inside.

Rotation + orientation EXIF.

Compression JPEG/PNG.

Suppression/conservation métadonnées.

Filigrane texte/logo.

Format non supporté → erreur applicative.

Erreur Sharp → erreur applicative structurée.

10.3 Fonctionnel par outil
Un fichier + lot.

Options valides + invalides.

Résultat téléchargeable correctement nommé.

Échec d'un élément sans perdre les autres du lot.

Comparaison poids/dimensions.

ZIP contient exactement les résultats demandés.

10.4 Qualité technique
TypeScript strict.

Aucun any injustifié.

Aucun faux résultat ni donnée simulée en prod.

Aucun import Sharp côté client.

Aucune duplication règles validation.

Aucune promesse fonctionnelle non supportée par le moteur.

Gestion erreurs + nettoyage ressources temporaires.

Vérification limites mémoire + durée traitements.

12. Définition de « terminé » pour une fonctionnalité
Une fonctionnalité n'est pas terminée parce que sa page s'affiche. Elle l'est quand :

✅ Son schéma valide les paramètres.

✅ Son endpoint valide les fichiers côté serveur.

✅ Son endpoint appelle le moteur central.

✅ Son hook client utilise le contrat réel.

✅ Son interface gère chargement, succès, erreur, lot.

✅ Le résultat est prévisualisable.

✅ Les propriétés/économies pertinentes sont affichées.

✅ Le téléchargement individuel fonctionne.

✅ L'export ZIP fonctionne (si pertinent).

✅ Tests couvrent cas nominaux + erreurs.

✅ Aucune dépendance serveur importée côté client.

✅ Limites et capacités annoncées = comportement réel.

Décision 1 — Plateforme de déploiement
Question
L'application tourne-t-elle sur Vercel, VPS ou Docker ?

Décision retenue
✅ Vercel (serverless)

Justification
Stack Next.js 16 + App Router déjà alignée sur Vercel.

Pas de maintenance d'infrastructure.

Déploiement continu natif via Git.

Conséquences architecturales
Timeout max : 60 secondes par requête (configurable jusqu'à 300 s en Pro). export const maxDuration = 60 obligatoire sur chaque route outil.

Pas de FS persistant : aucun fichier ne peut survivre entre deux requêtes sur le disque local.

Stockage temporaire : nécessite une solution externe (Vercel Blob, S3, R2) pour l'option C du Blocage 2.

Cold start Sharp : premier appel peut prendre 1-3 s (libvips à charger). À anticiper dans les skeletons UI.

Traitement par lot limité : 200 images × 25 Mo dépasse les 60 s → nécessite un traitement asynchrone ou un batch réduit.

Phases concernées
Toutes les phases API (6 à 11, 18).

Phase 11 (Export Manager) : stratégie de streaming ZIP à revoir pour Vercel.

Limites à intégrer dans lib/validators/image-limits.ts
ts
export const LIMITS = {
  MAX_FILE_SIZE: 25 * 1024 * 1024,      // 25 Mo / fichier
  MAX_BATCH_SIZE: 20,                    // 20 fichiers / requête (Vercel)
  MAX_WIDTH: 8000,                       // px
  MAX_HEIGHT: 8000,                      // px
  MAX_PIXELS: 100_000_000,               // 100 MP (anti decompression bomb)
  MAX_ZIP_SIZE: 500 * 1024 * 1024,       // 500 Mo ZIP
  MAX_CONCURRENT_PROCESSING: 4,          // p-limit(4) max
} as const;
Décision 2 — Stratégie de retour des fichiers traités
Question
Comment le navigateur reçoit-il un fichier traité ?

Décision retenue
✅ Approche hybride B + C :

Option B (Blob response) pour traitement unitaire (1 fichier).

Option C (Lien temporaire) pour traitement par lot > 5 fichiers.

Justification
Option B = la plus efficace pour 1 fichier (pas de base64 +33 %, pas de stockage).

Option C = indispensable pour lot (un seul JSON de réponse avec N URLs, pas N requêtes binaires).

Le seuil de 5 évite la complexité Blob pour les petits lots (2-5 fichiers).

Conséquences architecturales
Routes API — signature :

text
POST /api/images/convert
  Body: multipart/form-data (files[], options)
  
  Si files.length === 1:
    Response 200: Content-Type: image/webp
                  Content-Disposition: attachment; filename="photo.webp"
                  Body: <binary buffer>
  
  Si files.length > 5:
    Response 200: {
      results: [
        { id, filename, mime, size, width, height, url: "/api/temp/{id}" },
        ...
      ],
      expiresAt: "2026-11-07T13:00:00Z"
    }
Route temporaire (nouvelle) :

text
GET /api/temp/[id]/route.ts
  Response 200: Content-Type: <mime>
                Content-Disposition: attachment; filename="<filename>"
                Body: <binary buffer>
  Response 404: expiré ou inconnu
Stockage temporaire : Vercel Blob (à configurer) ou S3/R2 si préféré.

Variable d'env : BLOB_READ_WRITE_TOKEN (Vercel Blob) ou équivalent.

Chemin : {processId}/{filename}.

TTL : 1 heure (voir Décision 7).

Hooks client :

use-converter.ts gère les deux cas :

1 fichier → fetch + response.blob() + URL.createObjectURL().

5 fichiers → parse JSON + affichage des URLs dans ExportManager.

2-5 fichiers : traité comme lot (option C) pour simplifier la logique — un seul format de réponse.

Règle unifiée simplifiée
Nombre de fichiers	Retour
1	Blob response (option B)
2 à 20	JSON avec URLs temporaires (option C)
Révision par rapport à la question initiale : le seuil passe de 5 à 2 pour éviter de maintenir deux formats de réponse côté hook. Un seul fichier = Blob, plusieurs = URLs.

Phases concernées
Phase 6 : contrat documenté dans l'endpoint de référence.

Phases 7-11, 18 : toutes les routes.

Phase 5 : ExportManager doit gérer URLs.

Phase 11 : ZIP assembly depuis URLs temporaires.

Phase 20 : états UI distinguent "buffer prêt" vs "URL prête".

Décision retenue
✅ Optionnel — Phase 19 conservée en fin de roadmap.

Justification
PixelForge reste fonctionnel sans historique (outil de traitement one-shot).

Décision 6 — Algorithme de tolérance couleur (détourage, outil 07)
Question
Quelle formule mathématique pour la tolérance de détourage ?

Décision retenue
✅ Distance RGB euclidienne normalisée (v1 simple).

Formule
text
distance(pixel, target) = sqrt((r-r₀)² + (g-g₀)² + (b-b₀)²)

Si distance < tolerance * max_distance → pixel = transparent
Où :

max_distance = sqrt(255² + 255² + 255²) ≈ 441 (diagonale RGB).

tolerance ∈ [0, 1] (UI 0-100 %).

pixel et target = [r, g, b] en 0-255.

Justification
Simple : 3 lignes de code, aucune dépendance.

Prévisible : l'utilisateur comprend facilement "plus de tolérance = plus transparent".

Suffisant pour les fonds unis (blanc, noir, vert chroma-key).

Documentable : formule explicite dans la doc utilisateur.

Limites assumées
Pas perceptuel : un fond blanc et un sujet blanc auront la même distance (l'utilisateur baisse la tolérance).

Pas adapté aux dégradés complexes : hors périmètre (détourage IA).

Canal alpha ignoré : on traite des images opaques uniquement.

Upgrade v2 (hors périmètre)
Distance Lab (deltaE 2000) : meilleure perception, mais +30 lignes de conversion RGB→Lab.

Décision : si les retours utilisateurs le demandent, upgrade Phase 13.2 (itération séparée).

Conséquences architecturales
api/images/background/route.ts :

ts
function isTargetColor(r, g, b, target, tolerance): boolean {
  const dr = r - target.r;
  const dg = g - target.g;
  const db = b - target.b;
  const distance = Math.sqrt(dr*dr + dg*dg + db*db);
  return distance < tolerance * 441;
}
lib/image-engine/transformations/filters.ts : fonction removeUniformBackground(buffer, target, tolerance).

UI background-settings.tsx :

Pipette → sélectionne couleur sur l'image.

Slider tolérance 0-100 %.

Aperçu damier en temps réel.

Phases concernées
Phase 13 : implémentation complète.

Phase 4 : filters.ts inclut déjà la fonction.

Décision 7 — Nettoyage des fichiers temporaires
Question
Si option C du Blocage 2 (URLs temporaires) : qui nettoie et quand ?

Décision retenue
✅ Lazy cleanup : purge à chaque nouvelle requête des fichiers > 1 heure.

Justification
Pas de cron job à maintenir (simplicité Vercel).

Pas de TTL S3/R2 à configurer (moins de dépendances infra).

Auto-nettoyant : si l'usage est régulier, les vieux fichiers disparaissent d'eux-mêmes.

Compatible Vercel : chaque requête API est stateless, mais peut déclencher un cleanup opportuniste.

Mécanisme
Trigger : à chaque appel d'une route API image (/api/images/*), avant traitement :

ts
await cleanupExpiredFiles();  // best-effort, non bloquant
Fonction :

ts
// app/pixel/lib/storage/temp-cleanup.ts
const TTL_MS = 60 * 60 * 1000; // 1 heure

export async function cleanupExpiredFiles(): Promise<void> {
  try {
    const blobs = await list({ prefix: "temp/" });
    const now = Date.now();
    for (const blob of blobs) {
      if (now - new Date(blob.uploadedAt).getTime() > TTL_MS) {
        await del(blob.url);
      }
    }
  } catch {
    // best-effort : si le cleanup échoue, on ne bloque pas le traitement
  }
}
Non bloquant : si Vercel Blob API échoue, on continue le traitement normal. Le fichier restera 1 h de plus, sans impact utilisateur.

Aussi déclenché : lors de la suppression manuelle d'un résultat (UI ExportManager) → del(url) immédiat.

Quotas Vercel Blob
Hobby : 1 Go stockage, 100 Go bande passante (suffisant pour un usage perso/POC).

Pro : 100 Go stockage.

À surveiller : si usage intensif, ajouter un cron Vercel quotidien en complément.

Conséquences architecturales
Installation :

bash
npm i @vercel/blob
Variables d'environnement :

text
BLOB_READ_WRITE_TOKEN=vercel_blob_rw_xxx
Fichier nouveau : app/pixel/lib/storage/temp-cleanup.ts.

Route nouvelle : app/api/temp/[id]/route.ts (voir Décision 2).

Intégration : toutes les routes /api/images/* appellent cleanupExpiredFiles() en début de handler (fire-and-forget).

Phases concernées

Phase 6 : brancher cleanupExpiredFiles() dans l'endpoint de référence.
